AI-Assisted Development for Laravel Teams
Half-Day Follow-Up Agenda
Rabbies development team — In-person / Teams, half day (approx. 3.5 hours + break)
Purpose
A working session to check what’s actually stuck since the core day, tighten the team’s approach to spec-led
development, and go deeper on evaluating AI output — an area the team has flagged as light — before agreeing
what to trial next.
1. Quick retro
• What’s actually been used since the core day — which habits stuck, which didn’t
• Where the friction has shown up in real work: prompting, review, trust in output, team consistency
• Quick round-the-room or shared-doc capture rather than a long discussion — this sets the agenda for
the rest of the session
2. Reframe: chain vs spec-led
• Look at a current, real prompting chain from the team — a sequence of ad-hoc prompts used to build a
feature
• Set it side by side with a spec-led version of the same task: a single planning step that produces a
reviewable artefact before generation starts
• Discuss what changes: what’s checkable before code exists, what’s reusable across sessions, where
review effort moves to
3. Mob-write a real spec, end to end
The bulk of the session, working as a group on one real, upcoming story pulled from the team’s own backlog.
• Mob-write the spec for the story together — planning conversation, tightening, review
• Draft a first-cut team spec template as you go, so the format is theirs rather than borrowed
• Run the spec through to generated output, checking it against the story’s actual acceptance criteria
• Agree explicitly where a human sign-off stays non-negotiable, regardless of tooling — this is a team
decision to make out loud, not something to leave implicit
4. Evaluating AI output
A dedicated section, given the team’s flagged this as an area they’re light on.
• Where manual review and sign-off stop being enough on their own — consistency across runs,
regressions you won’t spot by eye, output that looks plausible but is wrong
• A lightweight way to think about evals: a small set of real cases with a clear pass/fail definition, run
consistently against the spec you’ve just built
• Using the story from Section 3 as the worked example — what would a handful of meaningful test
cases for that spec actually look like
• Where this could plug into the team’s existing test culture rather than becoming a separate discipline
5. Open Q&A
• Whatever’s come up in real work since the core day — Copilot behaviour, Boost, edge cases, anything
the team’s been storing up
• Not scripted — driven by what the room brings
6. Close: what to trial next
• Agree one or two concrete things the team will trial before the next check-in, including a first step on
evals
• Confirm ownership: who’s driving the spec template forward, who’s picking up evals, who’s watching
for where sign-off gets skipped
