# Module 1 — Retro Capture Template

**For the facilitator.** Set this up as a shared doc (or shared screen with someone typing) before the session starts. This isn't an individual exercise — it's the live capture tool for the quick retro.

---

## Format

Three columns. Keep entries short — a phrase or a sentence, not paragraphs. This is capture, not a design document.

```markdown
# Retro: Four Weeks Since the Core Day

## What's actually been used
-
-
-

## What hasn't
-
-
-

## Where the friction has shown up
(prompting / review / trust in output / team consistency — tag each entry)
-
-
-
```

---

## How to run it

1. Share the doc. Give the room 3–4 minutes to add entries individually (typing, not discussion) — this surfaces more honest answers than an open round-the-room, especially on a mixed-confidence team.
2. Read through what's there as a group, out loud, briefly. Don't discuss each point — just make sure everyone's seen the full picture.
3. If **PRD-driven development / `create-prd`** hasn't come up in either column, ask directly: "Did anyone use this since the core day? What happened?" Add the answer to the doc.
4. If **evaluating AI output** or a related friction (inconsistent results, trusting generated code, catching regressions) hasn't come up, note that too — it's coming in Module 3 regardless, but it's useful to know if the team has already felt the gap.
5. Anything that wants a longer discussion — park it. Add a `## Parked for open Q&A` section at the bottom of the doc and move it there. Revisit in Module 4.

---

## What this feeds into

- The **reframe** in the rest of Module 1 should reference specific entries from this doc, especially anything about spec-writing or prompting chains
- The **"parked" list** becomes the starting point for Module 4's open Q&A
- Keep the doc open for the rest of the session — it's useful context throughout, particularly if the mob-write session in Module 2 runs into a friction point someone already named here
